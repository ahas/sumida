## 1. 무엇인가

`.sz`는 sumida의 권한 규칙을 적는 언어다. 파일 하나가 "어떤 종류의 권한이 존재하고 그것들이
어떻게 조합되는지"를 선언하고, 부팅 때 파싱·검증을 거쳐 **SQL 술어로 컴파일된다.**

핵심 성질은 이것이다: 권한 판정이 애플리케이션의 조건문이 아니라 **쿼리의 일부**가 된다.
목록 조회의 `WHERE` 절이 규칙에서 만들어지므로 필터·`COUNT`·`ORDER BY`·`LIMIT`가 SQL 한
문장에 남는다.

규칙은 **정적**이고 배정은 **동적**이다. `.sz`에는 "manager라는 관계가 있고 계층을 탄다"까지만
적히고, **누가 manager인지는 한 글자도 없다.** 그건 관계 튜플이라는 데이터이고 런타임에
바뀐다. 조직을 새로 만들든 사용자를 뽑든 규칙은 그대로다.

## 2. 문법

```text
file        := ( definition | extension | namespace )*

definition  := 'definition' NAME [ 'on' TABLE '.' COL [ 'int' | 'uuid' ] ] '{' member* '}'

extension   := 'extend' NAME '{' member* '}'

member      := 'closure'    NAME 'via' NAME
             | 'relation'   NAME ':' relbody
             | 'permission' NAME '=' expr
             | 'scope'      NAME

relbody     := TYPE '=' derivation                     // 파생
             | subject ( '|' subject )*                // 저장

subject     := TYPE | TYPE '#' RELATION | TYPE ':*'

derivation  := 'column' '(' TABLE '.' COL '->' TARGET
                           [ 'of'    TABLE '.' COL ]
                           [ 'via'   TABLE '.' COL ( ',' TABLE '.' COL )* ]
                           [ 'where' <닫는 괄호까지 생 SQL> ] ')'

namespace   := 'namespace' NS [ 'service' ] [ '=' NAME ]

expr        := excl
excl        := inter ( '-' inter )*        // 가장 느슨
inter       := union ( '&' union )*
union       := term  ( '|' term  )*        // 가장 촘촘
term        := '(' expr ')' | NAME [ '^' ] | NAME '->' term | TYPE ':' ID '->' term
```

결합 순서에 주의한다. `-`가 가장 느슨하므로 `a | b - c`는 `(a | b) - c`다. 제외가 합집합
바깥에 걸린다는 뜻이고, 이건 의도된 설계다 — 차단이 부여를 우회당하면 안 된다.

## 3. 구성 요소

### `definition NAME on TABLE.COL [int|uuid]`

권한을 매길 대상 한 종류를 선언하고, 그것이 어느 테이블 어느 컬럼에 사는지 묶는다.

`on`이 필요한 이유는 컴파일 대상이 SQL이기 때문이다. 객체 id 표현식을 쓸 수 없으면 목록
필터를 만들지 못한다. `int`/`uuid` 구분도 필수다 — 관계 튜플의 리소스 id는 text로 저장되므로
uuid를 캐스트 없이 비교하면 Postgres가 거부하고, 계층 닫힘은 id가 정수여야 closure 테이블과
조인할 수 있다.

테이블이 없는 정의도 있다. `service`, `platform`, `delegation_scope`는 `on`을 생략하고 명시적
객체 id로만 닿는다.

### `relation NAME : ...` — 두 종류

**저장 관계.** 주체를 `|`로 나열한다. 관계 튜플로 부여하고 회수한다.

```
relation viewer: user | role#member | organization#member | apikey
```

`user:*`를 허용하면 로그인한 누구나 해당한다. 전체공개가 의미 있는 자리에만 선언한다.

**파생 관계.** `column(...)`으로 이미 있는 컬럼에서 읽는다. 부여할 필요가 없고 부여할 수도 없다.

```
relation owner: user         = column(files.user_id -> user where files.user_id IS NOT NULL)
relation org:   organization = column(files.user_id -> organization via users.organization_id)
relation member: user        = column(users.id -> user of users.organization_id)
```

파생이 존재하는 이유는 **표류 방지**다. 소유자는 이미 컬럼에 있다. 그것을 튜플로 한 벌 더
쓰면 둘이 어긋날 수 있고, 어긋나면 인가가 조용히 틀린다. 파생이면 컬럼이 곧 정본이라 표류가
구조적으로 불가능하다. 튜플은 컬럼으로 표현할 수 없는 것 — 공유, 차단, 위임 — 에만 쓴다.

`of`는 방향을 정한다. `column(users.id -> user of users.organization_id)`는 "이 객체를 조직으로
갖는 사용자들"이다. `of`가 없으면 "이 행의 작성자"와 문법적으로 구분되지 않는데, 둘은 정반대
의미다. `via`는 중간 조인 홉이고, `where`는 파생에 붙는 조건이다. `where` 안의 컬럼은 반드시
테이블명으로 한정한다 — 파생은 서브쿼리 안으로 들어갈 수 있고, 거기서 한정 없는 이름은 엉뚱한
테이블에 묶인다.

### `closure NAME via TABLE` 와 `^`

계층을 선언하고, `^`로 그 계층을 탄다.

```
closure parent via org_closure
permission manage = manager^
```

`manager^`는 "이 객체 **또는 그 조상 어디든**에 걸린 manager 튜플"이다. 조직 100에 관리자를
한 명 걸면 그 아래 나중에 생기는 조직까지 자동으로 따라온다.

미리 계산된 closure 테이블을 가리키므로 `^`는 조인 한 번으로 컴파일된다. 계층 깊이와 무관하게
비용이 일정하다. 재귀 CTE를 행마다 도는 형태였다면 목록 한 페이지에 수십 번 돌았을 것이다.

### `permission NAME = expr`

관계와 다른 권한을 조합해 실제로 검사하는 이름을 만든다.

| 연산 | 뜻 |
|---|---|
| `\|` | 합집합 |
| `&` | 교집합 |
| `-` | 제외 |
| `->` | 다른 정의로 이동 |
| `^` | 계층 닫힘 |

```
permission edit   = (manager | editor | service:document->operate_update) - blocked
permission view   = (viewer  | edit   | service:document->operate_read)   - blocked
```

권한 그래프는 **비순환이어야 한다.** 컴파일러가 그래프를 인라인해 한 문장으로 펴기 때문이고,
순환은 부팅 시점에 거부된다.

### `scope NAME`

조직 권한을 리소스 종류별로 쪼개는 매크로. 한 줄이 관계 3개와 권한 3개로 펼쳐진다.

```
scope file
```

가 이렇게 된다.

```
relation   file_viewer / file_editor / file_manager
permission view_file   = file_viewer^  | edit_file
permission edit_file   = file_editor^  | manage_file
permission manage_file = file_manager^ | manage
```

손으로 쓰면 종류마다 6줄이고, 그 6줄이 서로 정확히 같은 모양이어야 한다. 하나에서 `^`를
빠뜨리면 그 종류만 계층을 안 타는데 읽어서는 눈에 띄지 않는다. 매크로면 그런 어긋남이 생길 수
없다.

### `extend NAME { ... }`

**다른 파일에서 선언한 정의에 멤버를 더한다.** 정의 본문에 쓸 수 있는 멤버는 여기에도 그대로
쓴다 — 실제로 쓰이는 것은 대부분 `scope`다.

```
extend organization {
  scope widget
  scope ticket
}
```

한 정의를 두 파일이 선언하는 것은 거부된다. 이름 하나에 정의가 둘이면 같은 질문에 답이 둘이라는
뜻이라서다. 그래서 프레임워크의 `organization`에 자기 리소스 종류를 붙이려면 재선언이 아니라
**추가**가 필요하고, 그것이 `extend`다.

왜 있어야 하는가는 방향의 문제다. 어떤 종류의 리소스를 조직 단위로 나눌지는 **그 리소스를 가진
쪽**이 안다. 프레임워크가 그 목록을 들고 있으려면 자기를 쓰는 서비스들의 이름을 미리 알아야
하는데, 그러면 네 번째 서비스가 생길 때마다 프레임워크를 고쳐야 하고 세 번째 서비스의 이름이
네 번째 서비스의 바이너리에 실린다. `extend`는 그 목록을 소유자 쪽에 돌려놓는다.

두 가지는 확장에서 할 수 없다.

- **`on`과 `closure`를 다시 말할 수 없다.** 객체가 어디 사는지와 계층이 무엇인지는 정의의 정체성
  이지 멤버가 아니다. 그것까지 바꿀 수 있으면 재선언과 같아진다.
- **이미 있는 멤버와 같은 이름을 쓸 수 없다.** 부팅 실패다. 덮어쓰기를 허용하면 파일 하나를
  추가하는 것만으로 프레임워크의 권한 정의가 조용히 바뀔 수 있고, 그건 이 구문이 만들 수 있는
  최악의 결과다. 충돌은 시끄러워야 한다.

확장은 모든 파일을 읽은 **뒤에** 적용된다. 파일을 읽는 순서가 확장이 대상을 찾는지 여부를
바꾸지 않는다는 뜻이다. 대상이 아예 없으면 그것도 부팅 실패이고, 실패 메시지는 어느 파일의
어느 확장인지를 말한다.

### `namespace NS [service] [= NAME]`

라우트 게이트가 쓰는 네임스페이스 목록. 게이트되는 이름이 규칙과 짝이 맞는지 부팅 검증이 이
목록을 기준으로 확인한다.

## 4. 주체 표기

튜플의 오른쪽에 올 수 있는 것들이다.

| 표기 | 뜻 |
|---|---|
| `user:7` | 개인 |
| `role:3#member` | 그 역할을 가진 전원 |
| `organization:100#member` | 그 조직 소속 전원 |
| `apikey:<해시>` | 키 자체 |
| `user:*` | 로그인한 누구나 (허용한 관계에만) |

같은 관계 자리에 개인을 넣을지 역할을 넣을지 조직을 넣을지는 런타임 선택이다. 규칙은 "이 중
무엇이든 올 수 있다"고만 선언한다.

## 5. 부팅 검증

파싱과 검증은 요청을 받기 전에 끝난다. 규칙이 참조하는 테이블이나 컬럼이 실제 데이터베이스에
없으면 **서버가 기동을 거부한다.**

거부가 옳은 이유는, 그러지 않으면 술어가 조용히 다른 행을 고르기 때문이다. 그건 "인가가 틀린
채로 정상 서비스 중"이고 오류 응답 한 번보다 나쁘다. 실패는 눈에 띄어야 한다.

검증이 잡아내는 것들: 순환하는 권한, 없는 관계 참조, 선언되지 않은 주체 타입, 재귀 해석이
필요한 userset, 규칙 없이 게이트만 있는 네임스페이스, 없는 정의를 확장하는 `extend`, 이미 있는
멤버와 충돌하는 확장, 한 이름을 두 번 선언한 정의, 스키마와 어긋난 컬럼.

**규칙 파일은 여러 개일 수 있다.** 프레임워크가 자기 파일 하나를 싣고, 그것을 쓰는 서비스가
자기 파일을 등록한다. 등록은 규칙 집합을 처음 읽기 전에 끝나야 하고, 읽은 뒤에 등록하려 하면
거부된다 — 그러지 않으면 같은 프로세스가 어떤 요청은 프레임워크 규칙만으로, 다음 요청은 서비스
규칙까지 얹어서 판정하게 되고, 그건 배포 하나에 권한 모델이 둘이라는 뜻이다.

## 6. SpiceDB의 `.zed`와 다른 점

`.sz`는 Zanzibar 계열이고 SpiceDB 스키마와 겉모습이 닮았지만 **상위집합이 아니다.** 서로 다른
것을 최적화한 다른 언어다.

### `.sz`에만 있는 것

| | 이유 |
|---|---|
| `on TABLE.COL` | 인가를 SQL 술어로 컴파일하기 위해. 이것이 없으면 목록 필터를 만들 수 없다 |
| `column(...)` 파생 | 컬럼에 이미 있는 사실을 튜플로 중복 저장하지 않기 위해. 중복은 표류를 부른다 |
| `closure ... via` / `^` | 계층 탐색을 조인 한 번으로. 재귀를 행마다 돌면 목록 조회가 감당이 안 된다 |
| `scope` | 반복되는 3단 등급 선언에서 사람이 실수할 여지를 없애기 위해 |
| `extend` | 프레임워크의 정의에 그것을 쓰는 쪽이 자기 리소스 종류를 더할 수 있도록. 프레임워크가 소비자 목록을 들고 있지 않기 위해서다 |

### `.zed`에는 있고 `.sz`에는 없는 것

**임의의 재귀.** SpiceDB는 자기 참조 관계를 임의 깊이로 쓴다. `.sz`는 권한 그래프가 비순환이어야
하고, 계층은 미리 계산된 closure 테이블이 있는 것만 탈 수 있다. 새 계층을 도입하려면 closure
테이블과 그것을 유지하는 장치가 먼저 필요하다.

**조건부 권한.** "편집자이되 요청이 사내망일 때만", "평일 09시부터 18시까지", "금액이 한도
아래일 때만" 같은 것을 SpiceDB는 표현한다. `.sz`에는 튜플의 만료 시각 하나뿐이다.

**런타임 스키마 변경.** `.sz` 규칙은 배포로만 바뀐다. 대신 규칙 변경이 코드 리뷰를 거치고,
부팅 검증이 성립한다.

**분산 일관성 토큰.** SpiceDB는 권한 변경 직후의 낡은 읽기를 막는 장치를 갖는다. 단일
데이터베이스 트랜잭션 안에서는 실질적으로 문제가 되지 않지만, 기능으로는 없는 것이다.

**독립 서비스로서의 생태계.** 변경 구독 API, 감사 로그, 대량 반출입, 별도 도구. `.sz`는
프레임워크 안에만 산다.

### 왜 이 트레이드를 골랐나

넷 다 **같은 하나의 결정**에서 나온다. 권한을 API로 묻는 대신 SQL로 컴파일한다.

물어보는 방식으로 목록을 만들려면 후보를 뽑아 하나씩 확인해야 한다. 100건을 요청했는데 인가로
30건이 걸리면 70건만 나오거나, 채우려고 더 뽑다가 전체 개수가 틀린다. 페이지네이션이 구조적으로
깨진다. 수만 행짜리 목록 화면이 성립하지 않는다.

포기한 쪽은 재귀와 조건부다. 실제로 필요한 계층은 조직과 게시판 그룹 둘이고 closure 테이블
두 개로 덮인다. 조건부 권한은 아직 요구된 적이 없다.

표현력이 넓어진 게 아니라 **좁아진 대신 인가가 쿼리 안으로 들어왔다.** 좁아진 부분이 쓰이지
않는 부분이라 이득이 남는 것이지, 일반적으로 더 나은 언어라는 뜻은 아니다. 조건부 권한이
필요해지는 날이 이 선택을 다시 볼 지점이다.

## 7. 하지 못하는 것

- **개별 거부 튜플이 없다.** 차단은 규칙에 미리 자리를 만들어 둔 곳(`- blocked`)에서만 걸린다.
  임의의 부여에 "단 이 사람만 빼고"를 나중에 덧붙일 수 없다.
- **시간 조건은 만료뿐이다.** 튜플에 만료 시각을 줄 수 있지만 시간대나 요일 조건은 없다.
- **필드 단위가 안 된다.** 최소 단위는 행이다. "이 행은 보이되 이 컬럼은 가린다"는 규칙으로
  표현되지 않는다.
